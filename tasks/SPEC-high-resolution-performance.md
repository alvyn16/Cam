# Faster high-resolution capture and editing

Keep full-resolution source/export quality, synchronized audio, pause/cancel behavior, and working software/ProRes fallbacks. Measure the current release against the new paths using the same animated 4K source and real capture targets. Do not count faster request submission alone as faster decoding or recording.

Recording: hand owned, bounded D3D11 capture textures to the verified native Media Foundation hardware encoder without mapping full-resolution pixels to CPU memory. Crop/resize on the GPU, preserve constant frame pacing and paused time, keep native COM objects on their owning worker, and expose startup/runtime errors. Unsupported hardware/formats must select the established CPU/FFmpeg path before recording starts; do not silently restart an in-progress recording.

Editing: retain the responsive latest-request mailbox and reduced preview resolution, while avoiding repeated decoder-process startup where a native GPU decoder is available. Full-quality offline rendering/export remains independent of interactive preview resolution. Validate seeking/final frames, hardware failure fallback, rapid request cancellation, and bounded frame/device lifetimes.

Acceptance: before/after capture/decoder throughput, CPU and memory measurements; changing-color/pixel checks and independent full video decode; audio/camera/pause/cancel integration; standard regressions and native hardware tests. Report measured gains and limits, including any CPU transfers that remain. Do not describe unavailable GPUs or resolutions as live verified.

Initial profile: animated 3840x2160 HEVC 60 fps, eight seconds. CPU decode/scale to 1280x720 took about 3.0 seconds. D3D11VA with CPU scaling took 3.40 seconds and CUDA scaling took 6.50 seconds including startup. FFmpeg's D3D11 scaling failed texture allocation on this machine. These naive accelerator changes were rejected. Baseline fixtures and logs are under the temporary `cam-highres-95224f4974a6403ba19f9d5c75e0cbd8` directory; its original synthetic project clip duration must be extended to eight seconds before timeline comparisons.

Implemented scope: native display/area capture with four owned GPU textures at most, hardware identity verification and GPU crop/resize/color conversion on the capture adapter. Two-phase startup acceptance prevents an abandoned initialization from publishing a competing recording. Classic-window capture keeps its GDI occlusion recovery; ProRes, software selection and unsupported native startup use the established FFmpeg path.

High-resolution interactive previews use a persistent asynchronous Media Foundation reader, a one-sample completion slot and acknowledged flush on cancelled reads. Color conversion explicitly preserves BT.601/BT.709 and nominal range, including the BT.601 default of untagged legacy FFmpeg recordings. GPU area integration prevents aliasing in fine 4K detail. Reduced preview pixels still pass through CPU memory for the existing compositor upload; full-resolution export decoding remains independent. Sources at or below 1280 pixels keep the existing lightweight decoder unless hardware is explicitly required for diagnostics. Unsupported codecs/devices/matrices fall back once per source.
